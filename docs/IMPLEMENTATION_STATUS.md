# Implementation Status

This document describes behavior visible in the supplied client, server, and cryptographic-helper source. It separates the current prototype from features that remain design or implementation work. It is not a test-results report.

## 1. Implemented in the current source

| Area | Current behavior |
|---|---|
| Persistent identity | ML-DSA-65 private seed is loaded from a local file or generated by the helper when treated as unavailable |
| Ephemeral KEM | A fresh ML-KEM-768 keypair is generated for each handshake |
| Ephemeral classical exchange | A fresh X25519 keypair is generated for each handshake |
| Client identity | First-time registration sends an ML-DSA public key; later handshakes send a 64-byte identity token |
| Server identity | Client loads or bootstraps the server ML-DSA public key using TOFU |
| Client identity registry | Server associates identity tokens with ML-DSA public keys and caches resolved keys in memory |
| Signed handshake | ML-DSA-65 signs exchanged ML-KEM public keys and handshake-value payloads with distinct contexts |
| Hybrid secret material | Two directional ML-KEM shared secrets and one common X25519 shared secret are established |
| Directional key schedule | HKDF derives distinct AES keys, HMAC keys, and initial counters for each direction |
| Payload protection | AES-256-GCM encrypts each data-frame payload and authenticates the counter as AAD |
| Header protection | HMAC-SHA3-256 authenticates the three-byte header and incremented directional counter |
| Fragmentation | `write()` divides a byte string into frames no larger than `0xFFFFFF - 16` plaintext bytes |
| Message termination | A zero-length header and HMAC authenticate the end of a logical message and consume a counter value |
| Bidirectional exchange | Client sends a test payload; server receives it and sends a separate fixed test response |
| Receive loops | Client and server assemble frames until an authenticated terminator and then continue waiting for another logical message |

## 2. Current prototype behavior

The client connects to `localhost:6969` over IPv6 and sends:

```python
b"A" * (MAX_DATA_BYTES_PER_FRAME + 1)
```

The server receives and assembles that logical message. It then sends a fixed response with the same test length and content pattern. The response is not an echo of arbitrary request data.

Both sides currently report frame count and assembled payload length. The received application bytes are not routed into an email subsystem or stored in a mailbox.

## 3. Current implementation boundaries

- The current server response is fixed test data, not application-driven content.
- The client `write()` function increments a local counter variable but does not return the updated value. The current entry point calls it once; multiple separate writes on the same connection need a persistent per-connection counter state.
- The receive loops accumulate all fragments for a logical message in memory and do not apply an aggregate message-size limit.
- The AES-GCM nonce is generated randomly for each frame. The implementation does not maintain a per-key nonce registry or deterministic nonce allocator.
- The first server public key is trusted through TOFU unless it is provisioned and verified out of band.
- The handshake has individual signed payloads but no transcript-bound Finished/key-confirmation exchange.
- Key material is kept in ordinary files; hardened storage, permissions, rotation, and erasure need further engineering.

## 4. Future engineering work

### Protocol specification

- Define protocol versioning, handshake state transitions, transcript binding, and key confirmation.
- Specify identity provisioning, server-key rotation, pin recovery, and revocation behavior.
- Define limits for counter use and AES-GCM nonce use under a traffic key.

### Record and transport hardening

- Give send-counter state an explicit per-connection owner.
- Set maximum logical-message sizes and bound in-memory reassembly.
- Add handshake and record read deadlines.
- Ensure malformed or truncated records lead to consistent connection termination and resource cleanup.
- Define counter exhaustion and session rekey/termination behavior.

### Key management

- Apply restrictive filesystem permissions and safer atomic file updates.
- Avoid treating all key-read errors as equivalent to a missing key.
- Define identity rotation, recovery, and secure-erasure procedures.

### Email application layer

- Define accounts and authorization.
- Add mailbox and message storage.
- Implement submission, delivery, retrieval, and message identifiers.
- Add application-level duplicate/replay handling where required.
- Build a user-facing client and server-side message-processing path.

### Security review

- Complete a protocol specification before making security claims.
- Conduct adversarial review of the handshake, key schedule, record state machine, and key lifecycle.
- Obtain independent cryptographic and implementation review before handling real sensitive data.
